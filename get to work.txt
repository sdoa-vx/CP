2. Input Resolution (The @step.output Mechanism)
Pipeline steps can reference previous outputs:

json
"input": {
    "buffer": "@read_file.output"
}
Resolution rules:
If value is a string starting with "@":

Parse "@step_id.field"

Fetch runtime_graph[step_id].output[field]

If value is an object:

Recursively resolve fields

If value is a primitive:

Pass through unchanged

Implementation:
cpp
nlohmann::json resolve_inputs(
    const nlohmann::json& template,
    const RuntimeGraph& graph
);
This gives you dynamic dataflow.

3. JSON Merging (The Output Propagation Layer)
Capabilities return JSON.
Steps consume JSON.
Pipelines often need to merge:

static input template

resolved references

capability output

Merge strategy:
Object + Object → deep merge

Array + Array → replace

Primitive → replace

This keeps behavior predictable and deterministic.

4. Capability Invocation (The Heartbeat)
Inside the worker loop:

cpp
auto resolved_input = resolve_inputs(step.input_template, graph);
auto output = step.fn(resolved_input);
step.output = output;
Error handling:
Wrap in try/catch

On exception:

set error_flag_

record first_error_

decrement active_tasks_

notify main thread

This ensures no worker can poison the runtime.

ROOT CAUSE OF THE PARALLEL HANG (resolved):
The prior session correctly suspected the worker loop but mis-diagnosed it.
The real defect was a lost-wakeup race: worker threads decremented active_tasks_
and called cv_.notify_all() WITHOUT holding queue_mutex_ (the same mutex execute()
waits on). If a worker drove active_tasks_ to 0 in the window between execute()'s
predicate check and its sleep, the notification was lost and execute() blocked
forever. Each parallel run_pipeline() owns its own Scheduler, so ~1 run in N stalled.
FIX: all active_tasks_ decrements + the zero-notify now route through
Scheduler::finish_task(), which performs the fetch_sub and notify_all under
queue_mutex_. scheduler.hpp/.cpp bumped to v1.0.1.

[x] Phase 6.1 — Sandbox Enforcement (HONEST, enforceable core) — COMPLETE 2026-06-24
================================================================================
HONEST BOUNDARY: an in-process engine CANNOT syscall-sandbox arbitrary native
modules (a hostile .so can call open()/socket()/time() directly). True
confinement = out-of-process + OS sandbox (seccomp/namespaces) = a LATER phase.
6.1 enforces the declarative layer the engine genuinely controls.

[x] Determinism gate (pipeline-level, ENFORCED at graph build, both executors):
    pipelines deterministic by default; NONDETERMINISTIC/NETWORK caps rejected
    unless allow_nondeterminism=true (and not strict). Error:
    "NONDETERMINISM_NOT_ALLOWED: capability '...' is nondeterministic; set allow_nondeterminism".
[x] Capability flags: added CAP_NETWORK; registry add_flags(); Engine::set_capability_flags().
    Manifest + trace blocks now include "network".
[x] Module intent -> flags: loader normalizes module.json sandbox
    {fs,network,clock,random,env}; derives clock/random->nondeterministic,
    network->network and ORs onto the module's caps. Legacy array form still accepted.
[x] Foreign install/load policy (conservative, enforceable):
    - unsafe:true -> rejected at install (SANDBOX_UNSAFE_MODULE) + refused at load (loaded=false).
    - sandbox.network -> install refused unless `sdoa module install --allow-network`.
    - sandbox.fs:"read-write" -> refused unless `--allow-fs-write`.
[x] Built-in FileSystem already root-confined (real guarantee for first-party caps).
[x] CLI validate pipeline + dashboard visualizer respect allow_nondeterminism + network.
[x] ABI error codes: SDOA_ERR_NONDETERMINISM_NOT_ALLOWED, SDOA_ERR_SANDBOX_UNSAFE_MODULE.
