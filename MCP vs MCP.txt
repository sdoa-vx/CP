MCP vs MCP

In the SDOA Compendium, the term MCP is used internally to mean Migration & Compliance Pipeline, because within the doctrine it describes the constitutional executor that enforces SDOA’s rules. That’s the architectural process — the engine that validates manifests, runs compliance gates, and manages evolution.

|BUT| 

the Model Context Protocol (MCP)  — the Open VSX‑loadable standard — is the platform implementation we were building to make that pipeline accessible across editors (VS Code, VSCodium, Cursor, Zed, etc.).


. Dual identity summary (drop in README)
md
# SDOA MCP — Dual Identity

Internal:
- Name: SDOA‑MCP
- Meaning: Migration & Compliance Pipeline
- Role: Constitutional executor of the SDOA doctrine
- Scope: Enforces manifests, gates, lifecycle, innovation, and migration

External:
- Name: MCP (Model Context Protocol)
- Meaning: Standard protocol for tool integrations (VS Code, Cursor, Zed, etc.)
- Role: Exposes SDOA‑MCP as an MCP server
- Scope: Lets clients call SDOA‑MCP capabilities via MCP requests

Relationship:
- The VSX MCP server exposes the SDOA‑MCP engine.
- The SDOA‑MCP engine runs inside the MCP server.

6. Protocol contract between VSX MCP and SDOA‑MCP engine
6.1. MCP‑level request/response (Model Context Protocol)
ts
// src/mcp/protocol.ts

export interface SdoaMcpRequestBase {
  id: string;
  capability: SdoaMcpCapability;
}

export interface SdoaMcpResponseBase {
  id: string;
  success: boolean;
  error?: string;
}

export interface SdoaMigrateRequest extends SdoaMcpRequestBase {
  capability: "sdoa.migrate";
  payload: {
    projectRoot: string;
    targetPhase?: number; // 0–9 from Book III · The Migration
  };
}

export interface SdoaMigrateResponse extends SdoaMcpResponseBase {
  payload?: {
    phasesCompleted: number[];
    reportPath: string;
  };
}

// Similar shapes for validate, detectInnovation, mapReuse, plan, patch, audit…
The MCP server receives these via the Model Context Protocol SDK and forwards them to the engine.

6.3. Adapter between MCP server and engine
ts
// src/engine-adapter/index.ts

import {
  SdoaMcpEngine,
  EngineContext,
  MigrateOptions
} from "../../engine/src/index";
import {
  SdoaMigrateRequest,
  SdoaMigrateResponse
} from "../mcp/protocol";

export class EngineAdapter {
  constructor(private engine: SdoaMcpEngine) {}

  async handleMigrate(req: SdoaMigrateRequest): Promise<SdoaMigrateResponse> {
    const ctx: EngineContext = { projectRoot: req.payload.projectRoot };
    const options: MigrateOptions = { targetPhase: req.payload.targetPhase };

    try {
      const result = await this.engine.migrate(ctx, options);
      return {
        id: req.id,
        success: true,
        payload: {
          phasesCompleted: result.phasesCompleted,
          reportPath: result.reportPath
        }
      };
    } catch (err: any) {
      return {
        id: req.id,
        success: false,
        error: err?.message ?? "Unknown error"
      };
    }
  }

  // Similar handlers for validate, detectInnovation, mapReuse, plan, patch, audit…
}
This is the bridge: MCP requests in, SDOA‑MCP engine calls out, MCP responses back.

3. MCP server skeleton (src/mcp-server.ts)
ts
// src/mcp-server.ts

import {
  createServer,
  McpRequest,
  McpResponse,
  McpServer,
} from "@modelcontextprotocol/sdk";

import {
  SDOA_MCP_CAPABILITIES,
  SdoaMcpCapability,
} from "./mcp/capabilities";

import {
  SdoaMigrateRequest,
  SdoaMigrateResponse,
} from "./mcp/protocol";

import { EngineAdapter } from "./engine-adapter";
import { createEngine } from "../engine/createEngine"; // your engine factory

// 1. Bootstrap engine + adapter
const engine = createEngine(); // returns SdoaMcpEngine
const adapter = new EngineAdapter(engine);

// 2. Create MCP server instance
const server: McpServer = createServer({
  id: "sdoa-mcp",
  name: "SDOA Migration & Compliance Pipeline",
  version: SDOA_MCP_CAPABILITIES.engineVersion,
  capabilities: SDOA_MCP_CAPABILITIES.capabilities as SdoaMcpCapability[],
});

// 3. Generic dispatcher
server.onRequest(async (req: McpRequest): Promise<McpResponse> => {
  switch (req.capability as SdoaMcpCapability) {
    case "sdoa.migrate":
      return handleMigrate(req as SdoaMigrateRequest);
    // case "sdoa.validate": ...
    // case "sdoa.detectInnovation": ...
    default:
      return {
        id: req.id,
        success: false,
        error: `Unsupported capability: ${req.capability}`,
      };
  }
});

// 4. Capability handler(s)

async function handleMigrate(
  req: SdoaMigrateRequest
): Promise<SdoaMigrateResponse> {
  return adapter.handleMigrate(req);
}

// 5. Start the server (stdio / socket / http depending on MCP runtime)

async function main() {
  // For many MCP runtimes, stdio is the default transport:
  await server.listenStdio();
}

main().catch((err) => {
  // Minimal logging; real implementation should use proper logger
  console.error("SDOA MCP server failed to start:", err);
  process.exit(1);
});

5. Minimal extension entry (src/extension.ts)
ts
// src/extension.ts

import * as vscode from "vscode";
import { spawn } from "child_process";
import * as path from "path";

export function activate(context: vscode.ExtensionContext) {
  const disposable = vscode.commands.registerCommand(
    "sdoa.mcp.start",
    () => {
      const serverPath = context.asAbsolutePath(
        path.join("dist", "mcp-server.js")
      );

      const child = spawn(process.execPath, [serverPath], {
        stdio: "pipe",
      });

      // In a real MCP integration, the host (VSX / client) will connect
      // to this process via stdio or a socket; this is just the skeleton.
      console.log("SDOA MCP server started with PID", child.pid);
    }
  );

  context.subscriptions.push(disposable);
}

export function deactivate() {
  // no-op
}
This gives you:

A bootable MCP server using the MCP SDK

A single wired capability (sdoa.migrate) routed through the engine adapter

A stub engine that you can progressively replace with the real Migration & Compliance Pipeline


From here, you can:

Add the rest of the capabilities (validate, detectInnovation, mapReuse, plan, patch, audit)

Swap the stub engine methods for the real SDOA‑MCP implementation

Tighten logging, error handling, and transport (stdio vs socket) based on your actual MCP host
