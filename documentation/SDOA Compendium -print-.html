Section 01

Executive Summary

This section defines the constitutional mechanics of SDOA — how sovereignty, discoverability, and declarative wiring replace configuration and control.

SDOA is not merely a pattern; it is a constitutional architecture. Every module is a sovereign citizen, declaring its own identity, dependencies, capabilities, documentation, and lifecycle directly inside its own file. A lightweight registry discovers, validates, and wires the entire system at startup. There are no central configuration files, no manual registration steps, and no hidden dependencies.

SDOA is language-agnostic by design. The core contract — MANIFEST + DOCS + version — is identical across JavaScript, TypeScript, Rust, Python, and C/C++. As of v5.0 the architecture governs a full polyglot portfolio from UI atoms through backend workflows to compiled Rust engines, having evolved across five major versions since March 2026 and registering 147 modules at the time of documentation.

As of v5.4, the constitution ratifies the Sleeve module class — a sovereign boundary layer that lets the SDOA Engine govern, communicate with, and orchestrate systems it does not natively own (local CLIs, system daemons, remote APIs, language models, legacy utilities) without compromising internal safety, layer traffic laws, or structural determinism. The Sleeve formalizes the architectural threshold between the isolated SDOA core and the chaotic external world. See § The Sleeve Module Class.

Section 02

The Sovereignty Principle

Every module is a sovereign. A sovereign owns its source file(s), its manifest, its CSS (if a UI module), its data files (schemas, configs, catalogs), and its variants. It does not own files in another sovereign’s folder, any global shared directory, or any other module’s manifest.

Principle

Think of it like a well-run organization where each team owns its own work product. Teams communicate through official channels — not by walking into each other’s offices and editing files on each other’s desks.

Cross-sovereign communication happens only through declared interfaces: declared dependencies (requires), the EventBus, the StateStore API, and explicit service calls through the registry. Modifying another module’s internals, reaching into its folder, or monkey-patching are forbidden — not merely discouraged. A variant is an alternate implementation of a sovereign; it lives in that sovereign’s variants/ subdirectory, carries a full manifest, and declares variant_of.

Section 03

Three-Layer Architecture

Every operation flows through exactly three layers. There are no shortcuts and no layer-skipping. Information flows in one direction, structurally enforced by the way the system is built.

1
Features — Composition & Intent
Compose primitives from schema data, handle user intent, call adapters. Never touch the backend directly; never create DOM elements.
2
Primitives — Reusable Atoms
Render pixels, own their CSS, generic and reusable. No business logic, no backend calls. Receive config in, emit events out.
3
Adapters · Services · Workflows · Repositories
IPC, backend calls, state management, persistence, workflow execution. The backend the UI never reaches into except through declared contracts.
Traffic Rules
L1 → L2 only  ·  L2 → events only  ·  L3 ← L1 only
no layer skipping  ·  no circular dependencies

v5.4 Amendment · The Sovereign Integration

The Sleeve Module Class

A Sleeve is a sovereign boundary module whose sole purpose is to securely couple the SDOA Engine to an external system — local CLIs, system daemons, remote APIs, language models, or legacy OS utilities — without contaminating core framework safety. As the SDOA core became a stateful, fully unmocked local engine running inside IDE extension daemons, isolating its internal state machine from chaotic external mutation became a constitutional necessity. The Sleeve is that isolation, made law.

A Sleeve does not compute, orchestrate, or govern. It translates, relays, and normalizes input/output shapes. It is the only module class the constitution permits to expose non-SDOA systems as compliant SDOA capability surfaces. Architecturally it belongs exclusively to Layer 3, sitting as a defensive perimeter at the absolute edge of the substrate (see § 03, Boundary Topology).

Allowed
Raw data calls to external systems via explicitly declared, secure transports — CLI binaries, HTTP requests, or IPC bridges.
Forbidden
Mutating SDOA source files, modifying internal global state, or monkey-patching live module instances at runtime.
Normalization
All raw output passes through ResponseFormatter.service into { ok, data } / { ok, error } shapes.
Path Serialization
Every file path or execution route is declared and evaluated via PathResolver.service to prevent unauthorized traversal.

Inbound events are captured by the Sleeve, stripped of chaotic metadata, and normalized before broadcast to the EventBus. Outbound, only Layer 1 features or specialized Layer 3 workflows may invoke a Sleeve through the Registry; the Sleeve translates the clean SDOA command map into the transport syntax the external target requires.

GitSleeve.sleeve.js — the external interface block
static MANIFEST = {
  id:              "GitSleeve.sleeve",
  type:            "sleeve",
  layer:           3,
  runtime:         "NodeJS",
  version:         "1.0.0",
  operationalRole: "savant",
  external: {
    system:    "git",
    transport: "cli",
    path:      "auto",
    commands:  ["status", "commit", "push", "pull"]
  },
  capabilities: ["git.status", "git.commit"],
  requires:     ["ResponseFormatter.service", "PathResolver.service"],
  lifecycle:    ["init", "run", "dispose"]
};
Section 05

Lifecycle Contracts

Every module follows a documented lifecycle so the system knows when to initialize, render, update, and clean up. Strict lifecycle discipline prevents the class of bugs known as ghost listeners and memory leaks.

Frontend — Primitives & Features
initRegister listeners, load data. No DOM.
mountDOM attached. Render initial state.
updateState changed. Re-render only what changed.
unmountRemove listeners. Undo mount().
destroyPermanent retirement. Undo init().
Backend — Workflows & Repositories
initServer startup. Register self, load deps.
runPer-request. Return {ok, data/error}.
disposeShutdown. Close connections, flush writes.

The Action Surface

Introduced in SDOA 3.0 and part of every v4.0+ manifest, the action surface makes modules discoverable by capability. It is the foundation of AI-driven orchestration: the registry can auto-generate a system-wide command map, event graph, and workflow graph without reading any implementation code.

Section 10

EventBus & StateStore

The StateStore replaces all scattered window.* globals with a single reactive store; no module reads or writes global variables. The EventBus enables pub/sub communication without direct coupling. Modules subscribe in init() and unsubscribe in destroy() — watch in init means unwatch in destroy, or you leak.

StateStore.adapter.js
get(key)
set(key, value)
watch(key, handler)
EventBus.service.js
emit(event, payload)
on(event, handler)
Section 11

Backend Routing

The BackendConnector replaces manual switch statements with declaration-based routing. During init it scans every manifest’s backendDeps, builds a routing table, and dispatches automatically. Server-side, the Router converts each incoming message type to a PascalCase workflow id and dispatches to the matching *.workflow.js.

Adding a backend capability

Create one file. Dynamic routing discovers it — no switch statements, no registration steps.

{ ok: true, data: { … } }  ·  { ok: false, error: "…" }

The Law · 01

Build a Compliant Module

Six steps, in order. Architecture before code: verify the module belongs where you are putting it before you write a line of logic.

1
Verify placement (Gate 5)
Decide the layer and the owning sovereign. Fix the architecture first — never write code into the wrong place.
2
Write the file header (Gate 3)
Filename, version, ISO-8601 timestamp, and a change description. This is the audit trail for every file.
3
Declare the manifest
All eight v1.2 fields, plus v4.0 action-surface and v5.0 operational fields. A missing mandatory field is rejected by the registry at startup.
4
Implement the lifecycle
All five frontend methods (or three backend). Whatever mount() adds, unmount() removes.
5
Stay within line limits
Watch the per-type target; never approach the ~500-line hard limit. When in doubt: split first, optimize later.
6
Run the compliance checklist
Increment the version (Gate 4) and verify against the checklist below before marking complete.

The Law · 02

The Five Implementation Gates

The Gates govern how SDOA work is performed — not just how code is structured.

Gate 1 · Pending State
Files provided without instructions → enter a Pending state and wait. Do not act on assumptions.
Gate 2 · Atomic File Delivery
Deliver complete source files, never partial snippets. A complete file is always safe to drop in.
Gate 3 · Temporal Metadata Headers
Every file begins with the standardized header — the audit trail.
Gate 4 · Micro-Incrementation
Every alteration increments the patch version (1.0.04 → 1.0.05). A dense, traceable audit trail.
Gate 5 · Declarative Compliance
Before writing code, verify placement, dependencies, and lifecycle. Fix the architecture first.
The Law · 03

Layer & Variant Decisions

Which layer?
Renders pixels, no business logic? → Layer 2 · Primitive
Composes primitives into a screen? → Layer 1 · Feature
Talks to a server / DB / service? → Layer 3 · Adapter / Workflow
Does two of these? Split it.
Variant or canonical?
Same contract as an existing sovereign, different approach? → Variant
Functionally new purpose, no parent? → New canonical sovereign
If unsure, prefer variant — easier to merge back than to clean up a redundant canonical.

v5.4 · Sleeve Governance Gates

Boundary modules pass through the same governance sub-sovereigns as any other module, with rules specific to their external reach.

1 · ProbationOfficer Pre-Gate
Static analysis before indexing. Auto-rejects any Sleeve that embeds raw eval(), Function() constructors, or untracked file-system writes — and enforces the 500-line hard ceiling.
2 · Registrar Indexing Gate
Validates the completeness of the external block and registers dynamic routing, matching external binary targets to verified execution boundaries.
3 · Oracle Capability Mesh
Reads the declared capabilities arrays from valid Sleeves and maps them into the global capability surface, letting orchestrators safely leverage external tools.
4 · Triage Runtime Monitoring
Tracks the health of active Sleeves. If a system daemon crashes or an API drops, Triage intercepts the exception, prevents it from locking the IDE thread, and queues an explicit tracking item.

The Engine · 01

The Creation Pipeline

The Creation Pipeline (CP) is the generative executor at the heart of the Engine. Where the law constrains, the CP brings into being — it perceives the system, interprets intent, and produces new sovereign architecture end to end, every output answerable to the doctrine. Nine stages carry a need from first reading to a sealed, canonical change.

01 · Perception
Reads the system — its modules, manifests, and structure.
02 · Interpretation
Understands intent and the constraints that bind it.
03 · Innovation Detection
Identifies new opportunities and patterns worth forming.
04 · Reuse Mapping
Aligns intent with existing sovereign modules; avoids duplication.
05 · Planning
Generates a structured architectural plan before any code.
06 · Creation
Produces new manifests, modules, or variants — architecture, manifested.
07 · Compliance
Ensures every output satisfies the Law.
08 · Migration
Transforms existing systems into compliant sovereigns.
09 · Verification
Audits and seals the change into the canonical record.

The Engine · 03

The Innovation Detector

The discovery engine. It scans static analysis output, clusters repeated patterns using AST structural hashing and Levenshtein distance, and proposes new sovereign modules — routing each to its correct directory and integrating with the Reuse Mapper. It catches conceptual redundancy before the code is written.

Frequency Thresholds
≥ 3 occurrences → primitive or workflow. ≥ 2 → schema or engine. Mathematical conditions for refactoring, removing human bias.
Sovereign Routing
Hardcodes Layer 2 for primitives, Layer 3 for workflows. Schemas to ui/data/schemas/, matching the placement rules.
⭐ Portfolio Expansion Prompt

When the Detector finds a compliant, reusable pattern, it surfaces a voluntary choice:

[1] Save locally only
[2] Submit to the Federated Sync Network (FISP)
[3] Skip — mark as local-sovereign
The Engine · 04

Federated Sync — FISP DRAFT v1.1

The Federated Innovation Sync Protocol is the nervous system that lets MCP instances share innovations with the canonical repository. It is simple JSON over HTTP, pull-request friendly, and sovereign-aware: strictly opt-in, voluntary, and mediated by human-in-the-loop governance. Nothing auto-applies.

Innovation data model — SDOA-aligned

innovation.json
{
  "id": "uuid-or-hash",
  "type": "primitive | feature | adapter | service |
           workflow | repository | engine | schema |
           rule | exemplar",
  "name": "HumanReadableName",
  "version": "1.0.0",
  "source": { "language": "js|ts|rs|py|cpp|json",
              "content": "…", "path": "rel/path" },
  "sdoa": {
    "layer": "1 | 2 | 3 | null",
    "placement": "ui/primitives | server/workflows | …",
    "manifest": { "operationalRole": "savant",
                  "optimization": { "priority": "speed" } }
  },
  "metrics": { "usageCount": 3, "confidence": 0.95 }
}
