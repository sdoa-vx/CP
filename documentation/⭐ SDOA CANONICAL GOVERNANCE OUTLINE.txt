Under Edition 5.4, governance is legally unified with code creation and the visual aesthetic standard, operating as a strict, multi-tiered checklist for all system modifications.  SECTION 2 — THREE-TIER ENFORCEMENT MATRIXGovernance is not an afterthought; it is programmatically woven into the runtime environment at three distinct levels to ensure compliance before compilation.  2.1 Structural Level (The Physical Layout)Rule: The canonical folder structure acts as a permanent layout boundary. Files must live strictly alongside the specific sovereign layer that consumes them.  Enforcement: The creation of generic, shared "dumping ground" folders—specifically /assets/, /static/, /deps/, /resources/, /misc/, or /global/—is strictly prohibited. The presence of these directories triggers an immediate pre-flight build failure.  2.2 Declarative Level (The Manifest Contract)Rule: Hidden dependencies, inline hardcoded behaviors, or externalized configurations are illegal.  Enforcement: Every module must expose an authoritative header manifest block detailing its exact identity, layer classification, capabilities, and required modules. Missing mandatory parameters cause the system startup routine to instantly reject the file.  2.3 Automated Level (The Sandbox Verification Gate)Rule: No unverified code is ever allowed to run natively in production or core workspace tracks.Enforcement: The automated system engine launches code mutations inside an isolated runtime sandbox before allowing them into the canonical index. SECTION 4 — SYSTEM BOUNDARY & SLEEVE GOVERNANCE GATESBecause the ratified Sleeve Module Class (*.sleeve.js) bridges the internal state engine with unverified external environments (such as system CLIs, local daemons, and remote web APIs), it must obey an amplified set of governance rules.  4.1 The ProbationOfficer Pre-Gate (Static Safety)Before a Sleeve can register its path, the static analysis engine evaluates the codebase string. The ProbationOfficer automatically rejects any Sleeve payload that attempts to introduce un-tracked file system access or execute un-sandboxed strings using loose runtime shortcuts like eval() or dynamic Function() constructors.  4.2 The Registrar Indexing Gate (Structural Alignment)The framework inspects the manifest's dedicated external tracking parameter block. The Registrar validates that the system targets, transport lanes (e.g., CLI binaries, HTTP bridges), and command boundaries are explicitly typed and mapped to prevent security traversals.  4.3 The Oracle Capability Mesh (Discovery Verification)Once validated by the Registrar, the Oracle indexes the Sleeve's declared capabilities list. This maps the normalized external command footprint into the global capability surface, allowing automated workflows to leverage the external utility safely and predictably.  4.4 Triage Runtime Monitoring (Fault Containment)During live application runtime, the Triage engine continuously monitors boundary connection states. If an external daemon collapses or an API pipeline drops, Triage catches the exception, shields the active IDE thread from locking up, and logs a clean alert response. If an engineering need clashes with an architectural constraint, you must pass a formal amendment to update the framework.
